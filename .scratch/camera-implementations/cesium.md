# Cesium sensor visibility implementations

The closest Cesium implementations use the scene renderer's own shadow-depth pass from a spot camera at the sensor, then classify the rendered surface in a post-process shader. Cesium renders terrain through its normal scene pipeline into the sensor shadow map; the application does not need a second DEM mesh or a CPU visibility mask readback. This is a strong architecture reference for a Cesium renderer, but it depends on Cesium's shadow pipeline and does not transfer directly to Ridgeline's MapLibre terrain renderer.

## Viewshed leads

[supershunan/cesium-tools](https://github.com/supershunan/cesium-tools) documents a newer `createVisualFieldAnalysis` / `useVisualFieldAnalysis` workflow. Its [README](https://github.com/supershunan/cesium-tools#readme) describes visible/hidden coloring with post-processing plus a shadow map, horizontal/vertical angle and color options, and two-click interaction that previews while moving the mouse before fixing the result. It says terrain should be enabled and 3D Tiles must cast shadows for complete occlusion. The repository declares MIT and Cesium `^1.119.0`. This is a useful current UI/configuration reference, but source inspection could not be completed in this environment: the GitHub source-tree/raw fetches failed and shell access to GitHub was unavailable. Its interaction is a one-off analyst viewshed, not evidence of a moving airborne sensor implementation.

[zhangti0708/cesium-viewshed](https://github.com/zhangti0708/cesium-viewshed) is an older small demo. Its [README](https://github.com/zhangti0708/cesium-viewshed#readme) passes `horizontalAngle`, `verticalAngle`, and `distance` to `Cesium.ViewShed3D`; the [demo page](https://github.com/zhangti0708/cesium-viewshed/blob/main/index.html) adds the analysis over a 3D Tiles scene. The implementation is supplied as `src/cesium-viewshed.js`, but the fetched GitHub/raw pages did not expose readable source, and the repository root has no license file. The issue list includes an open report that it fails with CesiumJS 1.105.1 and a request about observer height. Treat it as evidence that the API shape exists, not a verified algorithm or reusable code reference.

## Practical lessons

- A Cesium spot shadow map can classify rendered terrain and shadow-casting objects in one sensor projection pass, then tint the result in a post-process. This is the main reusable algorithmic idea.
- Sensor position, aim, projection, and frustum outline must all update from the same pose. SensorShadow's current update path does not satisfy that; the video projector rebuilds them together when setters run.
- The examples use Cesium's shadow-map internals. Reuse the rendering approach only where the host engine owns compatible scene depth/shadow passes; for MapLibre, keep the terrain-aware camera computation in Ridgeline's renderer-specific path.
- The video-projector FOV convention is one angle plus aspect. Ridgeline's independent horizontal/vertical FOV contract needs an explicit projection conversion or a custom frustum.
- No inspected source or demo establishes acceptable end-to-end latency for continuously moving sensors. Treat shadow-map resolution and update cadence as measurements to make in the target app.
