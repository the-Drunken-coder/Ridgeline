# ResQ Viz: camera coverage fit

**Decision: reject as a drop-in camera-coverage implementation; retain as a useful terrain-raycasting reference.** I inspected the public `main` tree and raw source at commit [`de41cb23fb76b8f7e491450d5b3bc25633eb0c3a`](https://github.com/resq-software/viz/tree/de41cb23fb76b8f7e491450d5b3bc25633eb0c3a). The source implements the WebGPU terrain sensor primitive advertised by the older search result, but its consumers are mesh-link line of sight and LiDAR. I found no camera sensor cone or ground-coverage classifier in the current client tree.

The primitive CPU-voxelizes the procedural heightfield into a sparse brick map and rebuilds it when terrain changes. [`webgpu/world.ts`](https://github.com/resq-software/viz/blob/de41cb23fb76b8f7e491450d5b3bc25633eb0c3a/src/ResQ.Viz.Web/client/webgpu/world.ts) contains `createWorld` and `rebuildWorld`; [`webgpu/sensors.ts`](https://github.com/resq-software/viz/blob/de41cb23fb76b8f7e491450d5b3bc25633eb0c3a/src/ResQ.Viz.Web/client/webgpu/sensors.ts) contains `bootSensors`, which creates separate line-of-sight and LiDAR query managers over that world. The default world is 128³ voxels at 8 m each, or a 1,024 m cube.

[`webgpu/lidar.ts`](https://github.com/resq-software/viz/blob/de41cb23fb76b8f7e491450d5b3bc25633eb0c3a/src/ResQ.Viz.Web/client/webgpu/lidar.ts) implements `LidarScan`: a full 360° azimuth scan with configurable vertical FOV, rotated by the drone quaternion. [`effects.ts`](https://github.com/resq-software/viz/blob/de41cb23fb76b8f7e491450d5b3bc25633eb0c3a/src/ResQ.Viz.Web/client/effects.ts) sets the default scan to 16 × 256 rays, 45° total vertical FOV, 200 m range, and one scan per second. `EffectsManager._updateLidar` runs it per drone and renders terrain-hit positions as cyan Three.js points. This is a LiDAR point cloud: it does not draw a camera frustum or classify ground cells as visible or terrain-blocked. It has a vertical-FOV/range match, but no independently steered camera bearing or horizontal camera FOV.

The second consumer casts one ray between each linked drone pair; terrain hits reduce that mesh link's opacity in `effects.ts`. That is useful terrain occlusion logic, but it communicates link obstruction rather than camera coverage. [`cameraMode.ts`](https://github.com/resq-software/viz/blob/de41cb23fb76b8f7e491450d5b3bc25633eb0c3a/src/ResQ.Viz.Web/client/cameraMode.ts) only selects Free, Chase, or FPV viewing modes. Its camera/FPV UI is separate from the WebGPU sensor query path.

**Fit for Ridgeline:** partial algorithmic reuse. The heightfield voxelization and ray marcher could support a new directional camera-ray consumer, but camera bearing/elevation/FOV/range controls, ground-cell visible/blocked coloring, and camera-coverage lifecycle are not implemented here. Expect to adapt the sensor query layer and build the coverage overlay in Ridgeline rather than integrate an existing feature.
