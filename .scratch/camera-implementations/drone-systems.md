# Drone camera footprint and visibility systems

Inspected September 24, 2026. This is a source-oriented comparison of complete applications, not a package survey. Links to implementation files point to the relevant files; line anchors are omitted because the source pages could not be fetched with line-number fidelity in this environment. The project documentation provides the line-level behavior descriptions linked below.

## Finding

I did not verify one open-source drone ground-control application that combines a live telemetry-driven camera frustum, DEM ray intersections, and terrain occlusion in the same map layer. The closest useful pair is DJI Drone Metadata Embedder for a real drone-video footprint workflow and Esri's Dynamic Situational Awareness app for a moving-observer terrain viewshed. They solve adjacent parts of the problem with different assumptions.

| Project | What the system does | Telemetry and terrain | License and practical fit |
| --- | --- | --- | --- |
| [DJI Drone Metadata Embedder](https://github.com/CallMarcus/dji-drone-metadata-embedder) | A real geospatial-video application. Its 3D MapLibre view replays recorded aircraft/camera pose, draws the camera's ground patch with four rays, supports scrubbing and playback, answers which recorded seconds covered a clicked ground point, and can crossfade the reconstructed view with original footage. Its exported footprint is a camera-frustum projection: per-model FOV, gimbal heading/pitch when available, four corner rays intersected with a flat ground plane; near-horizon rays are skipped or capped. | Uses recorded DJI SRT/MP4 telemetry, not a live GCS stream. It renders a terrain surface underneath the camera and track, but the footprint itself assumes flat ground and does not classify intervening terrain as an occluder. The guide explicitly warns that terrain rising into the frame makes the patch approximate. Missing gimbal/FOV telemetry is surfaced as an estimate. | MIT. Best directly comparable product and UI reference for Ridgeline's current estimated footprint, temporal playback, and honest confidence states. Not a DEM-aware footprint algorithm. The [MIT license](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/LICENSE), [implementation: footprint projection](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/src/dji_metadata_embedder/geo/footprint.py), [implementation: 3D map](https://github.com/CallMarcus/dji-drone-metadata-embedder/tree/master/src/dji_metadata_embedder/geo), and [geospatial guide](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/docs/geospatial.md) are public. A [live demo](https://www.callmarcus.com/demo/) and [screenshots/feature walkthrough](https://callmarcus.github.io/dji-drone-metadata-embedder/geospatial/) are available. |
| [Esri Dynamic Situational Awareness for Qt](https://github.com/Esri/dynamic-situational-awareness-qt) | A complete field situational-awareness app with a dynamic, directed viewshed and line-of-sight overlay. It colors visible and blocked areas separately, considers the elevation surface and loaded 3D scene features, and recalculates as the observer moves. Its message feeds include airborne tracks. Relevant application wrappers are [`ViewshedController.cpp`](https://github.com/Esri/dynamic-situational-awareness-qt/blob/main/Shared/analysis/ViewshedController.cpp), [`GeoElementViewshed360.cpp`](https://github.com/Esri/dynamic-situational-awareness-qt/blob/main/Shared/analysis/GeoElementViewshed360.cpp), [`LocationViewshed360.cpp`](https://github.com/Esri/dynamic-situational-awareness-qt/blob/main/Shared/analysis/LocationViewshed360.cpp), and [`LineOfSightController.cpp`](https://github.com/Esri/dynamic-situational-awareness-qt/blob/main/Shared/analysis/LineOfSightController.cpp). | The app consumes moving feed entities and terrain/scene data. The docs say the analyses run on the device GPU over data currently drawn in the map; accuracy therefore follows the displayed elevation/scene resolution. This is genuine visible-versus-obstructed analysis, but the app's observer is a generalized entity, not a camera frustum reconstructed from drone gimbal telemetry. Strong architecture and interaction reference for the separate terrain-visibility layer, but ArcGIS/Qt code is not directly reusable in the MapLibre TypeScript app. Esri provides [screenshots and downloadable sample builds](https://esri.github.io/dynamic-situational-awareness-qt/); README cautions the prebuilt examples are unsupported for production. |

## What the primary docs establish

The [DJI geospatial guide](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/docs/geospatial.md) documents the footprint as a rectangle for nadir shots and a trapezoid for tilted shots; it describes the four camera-corner rays intersecting a ground plane, the near-horizon guard, and the no-DEM limitation. Its 3D terrain playback section shows the camera gaze moving with recorded telemetry and lists the terrain-approximation caveat. These are useful features to compare against the current implementation, even though the terrain relief is not used to clip the camera frustum.

The [Esri DSA guide](https://github.com/Esri/dynamic-situational-awareness-qt/blob/main/docs/README.md) documents dynamic feeds, airborne tracks, directed viewsheds, visible/blocked styling, and GPU recalculation as the observer moves. It explicitly limits accuracy to the resolution of data displayed in the map. This is the strongest real application reference found for the moving terrain-occlusion half of the requested behavior.

## Other systems checked

- **Mission Planner and QGroundControl:** prior research already established the inspected camera projection/survey geometry is fixed-plane, not DEM occlusion; see [the earlier comparison](../camera-alternatives/github.md).
- **ATAK-CIV:** the public release history documents a built-in sensor-FOV toggle and elevation-backed viewshed/DTED features. Public CoT `SensorFov` fields include azimuth, range, horizontal and vertical FOV, elevation, and roll. That is good evidence for a sensor-pose interchange model, but I did not verify the current implementation source well enough to claim ATAK intersects camera rays with terrain or supports drone gimbal telemetry in its native cone. Treat these as separate UI and telemetry references, not an exact algorithm match. [ATAK source](https://github.com/TAK-Product-Center/atak-civ), [release history](https://github.com/TAK-Product-Center/atak-civ/blob/main/VERSION.md).
- **OpenHD/QOpenHD:** the project is a real video and MAVLink telemetry ground-station stack, but the inspected app description covers video/OSD/settings and forwarding telemetry to a GCS. I found no implemented map footprint or terrain-visibility layer, so it is not a candidate for this feature. [QOpenHD](https://github.com/OpenHD/QOpenHD).
- **Paparazzi GCS:** the older GCS manual documents a live camera-footprint polygon, but Paparazzi has since moved to the separate PprzGCS application. I did not establish that the new GCS retains the feature or locate the old implementation, so I have not ranked it as a verified code example. [Manual](https://wiki.paparazziuav.org/wiki/GCS), [current PprzGCS](https://github.com/paparazzi/PprzGCS).

## Reusable lessons for Ridgeline

Keep the continuously updated camera patch and terrain visibility semantically distinct. DJI Embedder is a concrete reference for a fast frustum patch from telemetry, time-based playback, click-to-query coverage, and visibly labeling guessed pose/FOV. Esri DSA shows a separate viewshed/LOS overlay for terrain and 3D obstruction, driven by observer movement and bounded by displayed data resolution. Combining them in Ridgeline would mean updating the simple footprint from telemetry at the normal rate, while computing an explicitly approximate, lower-frequency terrain visibility overlay from the locally available elevation surface. Neither source demonstrates that an accurate DEM-clipped camera footprint can be refreshed at every drone telemetry sample in MapLibre.
