# Moving camera footprint and terrain visibility implementations

Research date: 2026-09-24. Focus: actual MapLibre/Mapbox/deck.gl/Threebox applications that combine a moving directional camera footprint with terrain occlusion. I inspected implementation source, not just package feature lists. No exact implementation of all requested behaviors turned up. The closest camera product is DJI Drone Metadata Embedder; MeshMap Planner is a useful source-level reference for GPU terrain visibility masks; GeoLibre remains a simpler static CPU viewshed.

## Closest camera implementation: DJI Drone Metadata Embedder

- **Project and demo:** [CallMarcus/dji-drone-metadata-embedder](https://github.com/CallMarcus/dji-drone-metadata-embedder), MIT. Its [geospatial guide](https://callmarcus.github.io/dji-drone-metadata-embedder/geospatial/) documents `flightmap --3d`; the map is generated locally as standalone HTML, so the guide is a feature/demo walkthrough rather than a hosted sample map.
- **Map and terrain:** The generated viewer uses MapLibre GL JS 5.24.0 and Mapterhorn/Copernicus DEM tiles. The [map generator](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/src/dji_metadata_embedder/geo/flightmap3d_html.py#L1-L18) describes its terrain contract; [terrain setup](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/src/dji_metadata_embedder/geo/flightmap3d_html.py#L201-L205) creates a raster DEM source and [terrain sampling](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/src/dji_metadata_embedder/geo/flightmap3d_html.py#L469-L475) calls `queryTerrainElevation`.
- **Camera and footprint:** [The gaze module](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/src/dji_metadata_embedder/geo/flightmap3d_gaze_js.py#L15-L28) explicitly says its four corner rays project to a flat plane at the drone's AGL datum and the fill is then draped. [The projection](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/src/dji_metadata_embedder/geo/flightmap3d_gaze_js.py#L33-L87) uses per-sample altitude, gimbal pitch/yaw, and horizontal/vertical FOV, with documented estimates when attitude or lens data is absent. During playback, [the ring updates into a MapLibre GeoJSON fill](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/src/dji_metadata_embedder/geo/flightmap3d_gaze_js.py#L133-L143); [the playback cursor interpolates position and drives the ghost camera](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/src/dji_metadata_embedder/geo/flightmap3d_gaze_js.py#L392-L447). Ghost mode also sets the map's vertical FOV to the recorded camera FOV ([source](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/src/dji_metadata_embedder/geo/flightmap3d_html.py#L512-L559)). The guide describes stepping and playback [here](https://callmarcus.github.io/dji-drone-metadata-embedder/geospatial/#ghost-camera-see-what-the-drone-saw) and the sweeping ground patch [here](https://callmarcus.github.io/dji-drone-metadata-embedder/geospatial/#cameras-gaze-what-the-camera-saw-and-when).
- **Occlusion and exact limitation:** The implementation samples terrain along only four corner beams and renders them as short fill-extrusion prisms; see [`beamFor`](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/src/dji_metadata_embedder/geo/flightmap3d_gaze_js.py#L201-L263). Its browser test builds a 600 m cliff and checks that beam prisms stop at the wall ([test](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/tests/browser/test_flightmap_gaze.py#L383-L462)). That same test explicitly records the limitation: the polygon ring still projects to flat ground, so a rising hillside can place the far corner beyond the real hit; DEM ray marching that changes the patch is out of scope ([test note](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/tests/browser/test_flightmap_gaze.py#L393-L398)). This is the closest product-level example for pose/FOV/playback, but it does **not** produce a terrain-intersected visible/blocked footprint mask. The guide repeats the flat-ground limitation ([docs](https://callmarcus.github.io/dji-drone-metadata-embedder/geospatial/#cameras-gaze-what-the-camera-saw-and-when)).
- **Maintenance and practical notes:** At research time, the GitHub API reports the latest release as v2.16.1 (2026-09-22), with 1,052 commits in the repository view. The relevant 3D camera work is actively tested in a Playwright browser suite. During free-running playback the four terrain-sampled beams are throttled to roughly 12 rebuilds/s, while the patch still changes on each telemetry sample ([code](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/src/dji_metadata_embedder/geo/flightmap3d_gaze_js.py#L89-L99), [playback test](https://github.com/CallMarcus/dji-drone-metadata-embedder/blob/master/tests/browser/test_flightmap_gaze.py#L519-L565)). This is implementation evidence, not a comparative performance benchmark.

## Terrain-mask reference: MeshMap Planner

- **Project and demo:** [ModerateWinGuy/MeshMap-Planner](https://github.com/ModerateWinGuy/MeshMap-Planner), a public TypeScript application with a [live app](https://moderatewinguy.github.io/MeshMap-Planner/). The fork was pushed 2026-09-21 at research time and declares GPL-3.0. Its UI exposes a selected-node viewshed and an optional live-recompute control ([component](https://github.com/ModerateWinGuy/MeshMap-Planner/blob/main/src/components/Viewshed.vue#L20-L70)).
- **What it implements:** A GPU raster that labels terrain cells visible or hidden from a selected radio node, draped over the map. The [WebGPU shader](https://github.com/ModerateWinGuy/MeshMap-Planner/blob/main/src/viewshed/gpu.ts#L1-L12) describes radial line marching and running maximum elevation angle; [the compute code](https://github.com/ModerateWinGuy/MeshMap-Planner/blob/main/src/viewshed/gpu.ts#L58-L80) samples terrain between observer and target, includes a curvature correction, and emits opaque/transparent visibility pixels. The [heightmap builder](https://github.com/ModerateWinGuy/MeshMap-Planner/blob/main/src/viewshed/heightmap.ts#L1-L15) says it uses the same DEM surface as the map; [the WebGL2 fallback](https://github.com/ModerateWinGuy/MeshMap-Planner/blob/main/src/viewshed/webgl2.ts#L1-L20) implements the same compute contract when WebGPU is unavailable. The app documentation describes DEM/DSM and building-height obstruction in its [viewshed controls](https://moderatewinguy.github.io/MeshMap-Planner/).
- **Fit and limits:** This is a close reference for computing and drawing terrain-visible versus terrain-blocked cells, including the GPU-to-raster-overlay shape. It models a radio node/receiver height and a 360-degree viewshed, not a camera's horizontal/vertical FOV cone, gimbal pose, moving camera, or projected frustum footprint. The optional live control is not evidence of continuous per-frame camera tracking. It is not a camera solution or a benchmark result.

## Known MapLibre baseline: GeoLibre quick viewshed

- **Project and demo:** [opengeos/GeoLibre](https://github.com/opengeos/GeoLibre), MIT, with a [live app](https://geolibre.app/). Its docs describe “Viewshed from here” as computing terrain visible from a clicked point and displaying a translucent overlay ([guide](https://github.com/opengeos/GeoLibre/blob/main/docs/user-guide/map-controls.md)).
- **Actual algorithm:** [`computeViewshed`](https://github.com/opengeos/GeoLibre/blob/main/packages/processing/src/terrain-viewshed.ts#L148-L175) walks a DEM ray from an observer to each target and marks a cell visible if it rises above every intervening slope; [`viewshedToRgba`](https://github.com/opengeos/GeoLibre/blob/main/packages/processing/src/terrain-viewshed.ts#L253-L270) produces a transparent/visible raster. The docs set the quick tool to a 1.8 m observer and preset radii, and say it omits curvature/refraction at its 50 km ceiling ([guide](https://github.com/opengeos/GeoLibre/blob/main/docs/user-guide/map-controls.md)).
- **Fit and limits:** Static, omnidirectional, clicked observer. No camera FOV, heading, altitude pose updates, or camera-frustum footprint. It is the simplest source to read for CPU ray visibility but is less similar to a moving drone than DJI's playback implementation.

## Search result

The best fit is split across projects: DJI has the moving, directional camera semantics and an explicit flat-ground polygon; MeshMap Planner has a GPU terrain-occlusion mask but a stationary omnidirectional radio observer; GeoLibre has a compact CPU viewshed. I did not find an implementation combining moving camera pose, directional FOV, and terrain-clipped visible/blocked footprint in the targeted MapLibre, Mapbox GL JS, deck.gl, or Threebox searches. Generic terrain layers, camera-frustum drawing, and static radio/observer viewsheds were not counted as exact matches. No performance claims are made across these projects.
