# Other-engine sensor camera implementation

Inspected OpenGlobus source at [`61757dbc`](https://github.com/openglobus/openglobus/commit/61757dbc79604e37b3e85192ca1945b94c982d2a), the repository's `master` HEAD observed on 2026-09-24. This is one concrete implementation beyond the Cesium, MapLibre, and drone-GCS candidates covered elsewhere.

## OpenGlobus: depth camera plus terrain projector

OpenGlobus has a working TypeScript/WebGL terrain projector, including a dynamic UAV example. Its [`DepthCamera`](https://github.com/openglobus/openglobus/blob/61757dbc79604e37b3e85192ca1945b94c982d2a/src/control/depthCamera/DepthCamera.ts) accepts near/far clipping distances, horizontal and vertical view angles, and perspective or orthographic mode. It creates a `PlanetCamera` and framebuffer with a floating-point color target plus a depth attachment. On each renderer `predraw`, [`DepthCameraHandler`](https://github.com/openglobus/openglobus/blob/61757dbc79604e37b3e85192ca1945b94c982d2a/src/control/depthCamera/DepthCameraHandler.ts) calls each camera's `frame()`. That pass renders the planet's selected terrain segments from the sensor camera, then eligible vector-layer objects, into the camera framebuffer.

[`ProjectorManager`](https://github.com/openglobus/openglobus/blob/61757dbc79604e37b3e85192ca1945b94c982d2a/src/renderer/projectors/ProjectorManager.ts) stores camera depth in a shared `R32F` `TEXTURE_2D_ARRAY`; it reattaches each camera framebuffer to its array layer so the depth render writes there directly. The [`projectors.glsl` visibility function](https://github.com/openglobus/openglobus/blob/61757dbc79604e37b3e85192ca1945b94c982d2a/src/shaders/common/projectors.glsl) projects each receiver into the sensor camera, rejects points outside the frustum, linearizes receiver and sampled camera depths, then uses a biased depth comparison (3-by-3 PCF by default) to compute visibility. [`ProjectorsPass`](https://github.com/openglobus/openglobus/blob/61757dbc79604e37b3e85192ca1945b94c982d2a/src/renderer/projectors/ProjectorsPass.ts) composites the resulting projector color or light over receiver surfaces. This is real terrain occlusion from the renderer's terrain geometry, rather than a footprint projected onto a flat plane.

The checked-in [`sandbox/projectors/projectors.js`](https://github.com/openglobus/openglobus/blob/61757dbc79604e37b3e85192ca1945b94c982d2a/sandbox/projectors/projectors.js) creates two cameras at geographic positions, aims them at terrain coordinates, sets horizontal FOVs, and enables projector and footprint/frustum displays. The project's author advertises a [live projector example](https://sandbox.openglobus.org/examples/projector) in [this post](https://www.reddit.com/r/geospatial/comments/1wj3f3w/camera_coverage_projected_onto_real_terrain_open/); I did not launch the live page in this review. The separate [`sandbox/uav/uav.js`](https://github.com/openglobus/openglobus/blob/61757dbc79604e37b3e85192ca1945b94c982d2a/sandbox/uav/uav.js) snapshots a camera pose into a UAV entity, then synchronizes the sensor camera's position and pitch/yaw/roll from its attached frustum entity on `predraw` before calling `camera.update()`. It uses a finite near/far range and excludes the UAV's own vector layer from the depth pass. This is a clear moving-pose pattern; the sample does not itself connect to an external drone telemetry feed.

## What the view shows

The projector's color/light contribution exists only on terrain receivers that pass the sensor-depth comparison, so terrain behind an intervening ridge loses the projected overlay. It does not render a separate red “blocked” surface or a complete visible/blocked raster. With `showFootprint` enabled, the optional red geometry is only a boundary polyline; `renderFootprint()` reads framebuffer pixels and samples the camera-image perimeter back onto terrain. The demo's depth preview is a grayscale depth visualization, not a blocked-area classification.

The fill/occlusion/composite path is GPU-side. The footprint outline is a separate CPU readback-and-sampling path, so the sample is not evidence that every auxiliary product stays on the GPU. The implementation's 64 depth-array layers and 8-projector forward-shader batch are configured limits, not performance measurements.

## Fit for Ridgeline

This is a useful pattern for dynamic viewshed rendering when the sensor depth pass and displayed terrain share one 3D terrain renderer: render scene depth from the sensor pose, then depth-test projected receiver points in a shader. OpenGlobus produces coverage on its own streamed planet terrain mesh and renderer. It does not plug into Ridgeline's MapLibre `CustomLayer` or its existing DEM mesh/cache; adopting this system would mean replacing the terrain renderer, while borrowing the algorithm would require integrating equivalent sensor-depth and receiver passes with Ridgeline's terrain representation. OpenGlobus does not establish a remedy for the separate mask readback already present in Ridgeline, and this review made no comparable timing measurements.
