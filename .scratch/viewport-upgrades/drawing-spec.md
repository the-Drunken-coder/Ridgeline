## Problem Statement

Map users need to draw useful ground boundaries and routes, exclude areas with polygon holes, and place individual edges at known distances and bearings. They need to see which directed edge a numeric field changes and whether a placement targets an existing vertex or edge. Drawing must remain usable while navigating terrain, working by touch or keyboard, and recovering from an interrupted gesture.

Consumer applications need complete changes they can validate and save atomically in their own storage. Flattening a drawing into geometry alone loses shape-specific editing information. A rejected save, invalid draft or interrupted gesture must preserve recoverable work without changing accepted application data.

## Solution

Extend the existing ground drawing draft with polygon holes, exact individual segment edits and optional visible-edge snapping. Keep the approved labeled tool rail and fixed inspector. The inspector's selected ring and segment identify the same directed edge in map feedback, including a visible direction arrow. Solid vertex snap rings and dashed edge snap rings identify the target type.

Retain one drawing draft for the exterior, holes, appearance and label. Users can correct invalid geometry and undo draft edits; only valid completed changes can be submitted. Touch taps place points, handle drags edit them, and two fingers navigate throughout the draft. Interrupted gestures preserve applied draft work as an undoable action and release transient input ownership.

The consumer accepts or rejects the exact complete proposed change and owns persistence, permissions and accepted-change history. Ridgeline publishes the accepted change to the viewport. Geometry and versioned shape metadata remain together through storage and reload.

## Implementation Decisions

- The drawing session owns draft geometry, validation, measurements, draft history and submission phase. The map attachment owns screen-to-ground resolution, snapping, gesture ownership and draft feedback. Optional controls own field interaction and synchronize the active segment with the attached editor. The consumer owns authoritative data, persistence, networking, permissions and accepted-change undo.
- Precision uses the existing spherical Earth radius of 6,371,008.8 meters. Segment length is horizontal spherical distance; bearing is the initial direction clockwise from true north. Terrain slope, exaggeration and camera zoom do not change these values. Metric and imperial units affect display only; stored dimensions are meters and bearings are degrees.
- A numeric segment edit holds its start fixed and moves its end. An omitted distance or bearing retains that value. Other vertices stay fixed, so an adjoining edge sharing the moved endpoint can change. Editing a closing polygon edge moves the ring's first vertex. Numeric input makes an immediate adjustment and creates no persistent constraint.
- Segment addresses use an ordered ring and an index within that ring. Ring zero is the exterior or line; positive ring numbers address holes. The existing inspector chooses the ring and segment. The attached editor highlights that directed segment and shows an arrow whose head remains visible beside its endpoint handle. Changing feedback alone does not change geometry or draft history. Clearing or replacing the draft clears obsolete feedback.
- Active directed-segment feedback uses a 24 CSS-pixel head centered nine CSS pixels behind the endpoint. Broader wings fit between endpoint and insertion handles on the exercised short edge. Ordinary saved and draft arrow tools retain their existing presentation. This is a legibility correction within the approved feedback, not a new visual direction.
- Polygon shape definitions contain an open exterior ring and optional open hole rings. Generated GeoJSON closes every ring. Holes extend version 1 drawing metadata additively, retaining existing single-ring drawings. Consumers preserve both geographic geometry and the shape definition with saved appearance and application properties.
- Holes are general shape editing. A future disc or ring workflow is context for that capability; this delivery adds no dedicated disc or ring tool.
- Hole creation requires a valid current polygon and no hole already being placed. Point placement then addresses the new hole. Finishing a ring ends placement without submission. Hole deletion can remove an unfinished hole. Finishing the drawing submits the complete shape through the existing acceptance boundary.
- Holes must lie strictly inside the exterior, cannot touch or cross another boundary, and cannot overlap or nest. Existing restrictions on self-intersections, degenerate edges, polar shapes and hemisphere-scale shapes remain. Geometric invalidity stays in the draft with textual validation and blocked submission. This scope does not add validator error locations or automatic topology repair.
- Polygon area subtracts hole areas, perimeter includes every ring, and translation moves every ring. Translation is a geographic edit rather than a promise to preserve all entered dimensions during arbitrary relocation. Existing shape-specific circle and rectangle controls remain intact.
- Measurements on invalid drafts are provisional raw calculations. Valid geometry and hole topology are required for meaningful area. An oversized or outside hole can produce negative raw area; overlapping holes can subtract the same geographic area more than once. The session preserves these raw values without clamping. Drawing controls show "Area unavailable" while the measured shape is geometrically invalid and restore a meaningful area when undo returns it to validity. Keep invalid drafts editable and undoable, block submission, and retain textual validation without an error-location API. This control correction was approved on 2026-10-12 within the existing rail and inspector.
- Each committed numeric field change and standalone hole or vertex operation participates in existing draft history. Repeated handle movement groups into one gesture action. Undo and redo affect the draft, while accepted-change history remains with the consumer. Canceling the draft leaves accepted features unchanged.
- Vertex snapping remains enabled by default and edge snapping is opt-in. Both target eligible visible ordinary ground GeoJSON and saved ground drawings within the existing 12 CSS-pixel tolerance. Entity representations are outside this ground drawing target domain. Vertices take precedence when an edge is no more than one CSS pixel closer. The consumer filter applies to both target types. Snapping copies a position and creates no attachment or continuing constraint.
- Edge targets follow displayed segments under current projection, terrain and world-copy behavior. Screen-derived placement requires valid ground before snapping. Callback-driven changes to the scene, draft or owner invalidate the old target before it can be applied. Unavailable ground retains the last applied draft geometry.
- Snap feedback uses solid rings for vertices and dashed rings for edges, with the existing displacement guide. Alt bypass and the inspector's master snapping switch remain available without per-point confirmation. The edge preference survives temporarily disabling the master switch. Disabling visual feedback does not disable target validation or snapping.
- One finger places or edits throughout an active touch draft; one-finger canvas dragging does not pan even after placement ends. Two fingers navigate throughout the draft. Finish and Cancel remain explicit controls, with no double-tap completion. Handle hit areas remain usable without obscuring geometry.
- Multi-touch, pointer cancellation, capture loss, blur, scene/style/context loss, and lost edit permission release transient gesture ownership and clear obsolete targeting. Unrelated live feature updates and programmatic camera frames invalidate in-flight screen targeting without ending a mouse or touch gesture; a touch tap resolves its ground and snapping at release. Native camera navigation transfers gesture ownership. This interruption policy was clarified by the user during integration on 2026-10-13. Applied draft work remains one undoable gesture. Multi-touch suppresses accidental placement until all fingers lift. Recovery permits later valid input without stale movement or placement.
- Existing mouse navigation, keyboard handle operations and focus preservation remain. Keep the approved rail and fixed inspector with dense labeled fields, readable narrow layouts and state feedback. No decorative cards, pills, idle animation or substantial visual redesign is introduced.
- Submission provides detached complete before-and-after snapshots and an abort signal. The consumer atomically checks the baseline and saves the exact proposal, then accepts or rejects it. Ridgeline applies an accepted change to the viewport; the submit callback does not also mutate that viewport. Acceptance returns no normalized replacement feature or server-assigned identity.
- Pending submission locks editing and duplicate submission. Rejection preserves the draft. An external update to the edited feature preserves the draft, aborts pending work and requires restart or cancellation; unrelated updates do not interrupt it. Lost permission, replacement or destruction prevent obsolete acceptance. The consumer's storage must enforce baseline or version checks because abort cannot undo an external write.
- Existing callback diagnostics, permission recovery and snapshot isolation remain. Geometry-only edits to ordinary imported features retain their ordinary geometry and consumer-controlled appearance; Ridgeline does not infer shape definitions from flattened geometry. Saved shape metadata is validated against geometry using the existing documented rounding tolerance and topology contract.
- The starter demonstrates consumer-owned browser storage, complete drawing restoration, recoverable rejection and retry. Its storage format and UI are example application behavior, not a library storage service. Drawing attachments retain explicit destruction, automatic retirement with their viewport and safe repeated cleanup.

## Testing Decisions

- Use the existing installed-package consumer workflow as the primary integration boundary. Exercise drawing, numeric edits, holes, feedback, save, reload, rejection, retry and teardown through public interfaces and real browser input. No new testing-only export or internal seam is needed. These boundaries follow the already accepted testing approach.
- Test observable outcomes rather than source text, private call sequences or mocks that remove the real failure mode. Assert stored features, detached snapshots, visible map feedback, accessible controls, focus, camera changes, draft history and submission state as appropriate.
- Retain focused drawing-session and geometry tests for exact endpoint edits, closing edges, invalid ring addresses, hole topology, area and perimeter, all-ring translation, date-line and high-latitude behavior, undo grouping and storage round trips. Prefer the existing session and feature-validation interfaces.
- At the public drawing-session boundary, begin with an accepted valid polygon and hole, enlarge the hole beyond the exterior so its area exceeds the exterior's, and observe both validation and negative raw area. Verify the invalid draft remains editable and undoable, Finish cannot submit it or change accepted data, and undo restores valid topology and meaningful positive net area. At the packed control boundary, make the invalid edit through the numeric inspector, require "Area unavailable" and blocked Finish, then undo and require the meaningful displayed area to return. The session observation is implemented and passed locally on 2026-10-12; the packed observation is implemented passed in the current three-engine support run.
- Extend the prior packed drawing workflows to verify ring and segment changes identify the current directed edge, its direction remains visible beside handles, edits and undo keep feedback coherent, and ending or replacing a draft removes obsolete feedback. Verify feedback selection itself does not mutate geometry or history.
- The packed drawing workflow must establish that the direction head remains visibly distinguishable with its endpoint edit handle present. Observe composed map and handle pixels after segment/ring changes, numeric edits and undo. Compare the same composed scene with only the head shown or hidden and opacity transitions disabled. Require at least six CSS square pixels of visible green ink in each off-shaft wing. Unchanged shaft pixels and handle glyphs contribute no ink; antialiased head pixels contribute their visible coverage. Temporarily enlarge the real endpoint handle to cover the head, require both wings to disappear, then restore the handle and visible head. A `queryRenderedFeatures` identity or presence assertion alone cannot establish visibility. Existing manual captures remain valid evidence for their recorded scenes. The automated pixel assertion and legibility correction are implemented, with successful execution in all three engines recorded in the shared closeout. They establish the existing visible-direction requirement within the approved visual direction.
- Use the existing edge-snapping browser workflow for solid vertex rings, dashed edge rings, opt-in behavior, visible eligibility, Alt bypass, filter failures, terrain availability and callback-driven camera or scene invalidation. Test the displayed target rather than relying on an isolated segment calculation.
- Use native browser input for touch placement, handle movement, cancellation and two-finger navigation, plus mouse and keyboard behavior. Verify no extra point or movement after interruption, one undo action for the applied drag, and a usable next gesture. Engine-emulated touch is separate from physical-device acceptance.
- Retain submission and recovery histories at the public session boundary: pending locks, duplicate Finish, rejection and retry, external same-feature updates, permission loss and repair, callbacks that replace active work, destruction and late settlement. Assert both the abandoned action and the replacement's usability.
- Use the existing starter recipe workflow to save complete geometry and metadata, reject a save without losing the draft, retry, reload storage, reopen the drawing and dispose controls. Build the starter through its own documented dependency installation against the packed package.
- Check readable narrow layouts, named controls, native focus continuity and one action per shortcut across the exercised browser engines. Keep manual screen-reader and physical-device results distinct from automated evidence.
- Preserve the shared closeout's historical revision pins and acceptance mapping. Record current runtime checks and integrated review separately through root, tied to the uncommitted inputs actually exercised. Focused spec changes also require link and diff checks.

## Out of Scope

- Application storage services, networking, authentication, authoritative versioning or accepted-change history inside Ridgeline.
- A normalization handshake, server-assigned drawing IDs during acceptance or a returned canonical replacement feature without a demonstrated consumer requirement.
- Persistent dimension constraints, a constraint solver, automatic polygon repair or a validator error-location model.
- A dedicated disc or ring drawing tool.
- Changed one-finger navigation during a draft, double-tap completion or a new pen-specific input workflow.
- Survey-grade ellipsoidal or terrain-slope measurements, coordinate-system conversion, multipart or collection geometry, and general GIS analysis.
- Motion/history controllers, clocks, interpolation, retention, replay, timeline scrubbing and camera-follow policy. Consumers continue supplying current geometry and pose.
- A new visual direction, decorative UI or idle animation.
- Publishing a package, website, tracker issue or pull request; committing, pushing, deploying or merging this local work.
