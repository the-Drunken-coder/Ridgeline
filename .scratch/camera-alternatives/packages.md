# Camera footprint and terrain visibility alternatives

Research date: 2026-09-24. Scope: existing packages for a moving drone sensor in a TypeScript MapLibre GL JS 6.11 viewport, prioritizing approximate camera awareness and lower ownership.

## Recommendation

If a directional footprint is enough, keep MapLibre and reduce the feature to a GeoJSON footprint/fan, heading line, and normal fill/line layers. A small amount of camera-to-ground geometry remains application logic. Add `@turf/destination` only if geodesic endpoints are useful; it computes a destination from a starting point, distance, and bearing with the Haversine formula, but it does not compute a camera view or a viewshed. Turf is MIT-licensed and its repository was actively releasing in 2026. [Turf destination API](https://turfjs.org/docs/7.1.0/api/destination), [Turf repository and license](https://github.com/Turfjs/turf).

This is the lowest-total-ownership fit because it uses the renderer already in the package and avoids analysis textures, sensor depth passes, asynchronous pixel readback, and another renderer. It communicates where the camera points and an approximate ground footprint. Terrain may still be visible underneath/draped by the map, but the overlay does not test each point against intervening hills. The project’s own [camera lessons](../../docs/camera-lessons-learned.md) and [camera diagnostics](../../docs/camera-diagnostics.md) make that distinction explicit.

I did not find a maintained, drop-in MapLibre package that accepts a drone pose, FOV, range, and terrain and returns a terrain-occluded view. GeoLibre is a useful counterexample to “MapLibre cannot show a viewshed”: it ships a point-based quick viewshed in its full MIT-licensed GIS app, with a configurable observer height defaulting to a standing person and preset ranges, but it is not a reusable drone-camera component. MapLibre itself provides custom WebGL layers, including shared-depth rendering, but its API leaves rendering, GPU state, lifecycle, and any offscreen-depth work to the custom layer author. That extension point enables a bespoke analysis; it does not outsource it. [GeoLibre quick viewshed](https://github.com/opengeos/GeoLibre/blob/main/docs/user-guide/map-controls.md), [GeoLibre repository](https://github.com/opengeos/GeoLibre), [MapLibre CustomLayerInterface](https://maplibre.org/maplibre-gl-js/docs/API/interfaces/CustomLayerInterface/), [MapLibre terrain example](https://maplibre.org/maplibre-gl-js/docs/examples/3d-terrain/).

## Important capability boundaries

- A **frustum or footprint** represents camera direction and FOV. It can be drawn above the terrain or intersected with a simple ground model.
- A **viewshed** colors/classifies terrain based on whether terrain or scene geometry blocks the observer-to-ground path. GeoJSON draping, a camera wedge, and ordinary map occlusion do not compute this classification.
- **Camera-video projection** maps actual camera pixels onto terrain. None of the shortlisted APIs documents drone video-texture projection. That requires video/calibration inputs and renderer-specific texture projection; a viewshed is not a video feed.

For MapLibre, there are three practical routes: keep only the directional footprint; adapt GeoLibre’s separate TypeScript worker viewshed while supplying moving-camera and DEM integration; or adopt a renderer with a ready-made sensor analysis (ArcGIS or licensed Cesium ion SDK). GeoLibre’s quick action is point-based and has no heading/FOV camera API; its O(n³) worker cost and seconds-long main-thread fallback make it a reference for adaptation, not a ready-made moving-camera solution. The Whitebox WASM viewshed is a separate toolchain. No reviewed option is a simple maintained drop-in package for terrain-aware moving-camera classification in the existing MapLibre setup.
