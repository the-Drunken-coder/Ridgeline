# GitHub implementation research: camera footprints and terrain viewsheds

Inspected September 24, 2026, against the alternatives in [current-system.md](current-system.md). This is source-level comparison, not a benchmark or a package recommendation. Repository links below point at moving `main`/`master` branches; the browser and shell retrieval paths did not expose full commit SHAs, so pin a SHA before relying on a source snapshot.

## Recommendation

For the requested “where is the camera pointed, approximately what ground does it cover?” display, the simplest fit is the existing four-ray ground footprint in Ridgeline. MissionPlanner confirms that camera pose, FOV and pixel rays can produce a useful projected footprint against a constant-height ground plane. It does not compute terrain visibility. Treat that shape as an estimate, optionally drape it over MapLibre terrain, and avoid implying that hills were tested.

If terrain occlusion is a separate user-facing need, GeoLibre is the most relevant architecture reference because it is TypeScript, already uses MapLibre terrain, accepts observer height above ground, bounds the analysis window, and runs the computation in a Web Worker. Its actual algorithm is still a CPU ray walk with documented multi-second worst-case behavior; it is a paused/on-demand analysis pattern, not evidence for per-frame drone updates. A camera version would also need to limit the omnidirectional result to the camera’s FOV.

## Candidates

| **1. MissionPlanner** — [CameraProtocol.cs](https://github.com/ArduPilot/MissionPlanner/blob/master/ExtLibs/ArduPilot/Mavlink/CameraProtocol.cs#L565-L597) | `CalculateImagePointLocation` uses the reported camera and image-center locations plus HFOV/VFOV to project a normalized image pixel to the image-center altitude plane. | **2. GeoLibre** — [terrain-viewshed.ts](https://github.com/opengeos/GeoLibre/blob/main/packages/processing/src/terrain-viewshed.ts), [worker](https://github.com/opengeos/GeoLibre/blob/main/packages/processing/src/terrain-viewshed.worker.ts), [merged PR #1826](https://github.com/opengeos/GeoLibre/pull/1826/files), [map-controls guide](https://github.com/opengeos/GeoLibre/blob/main/docs/user-guide/map-controls.md) | This is actual terrain LOS: for each target cell, it walks intermediate DEM cells and compares their slopes from the observer. `ViewshedObserver.heightMeters` is configurable above local ground. It assembles Terrarium elevation tiles into a Float32 grid, computes a Uint8 visibility grid, then paints an RGBA overlay. The UI is a user-invoked analysis with 2/5/15 km presets and a 50 km maximum; the guide says it ignores earth curvature/refraction. | Strongest same-stack pattern: bounded DEM + plain typed arrays + worker + raster overlay. Source comments describe O(n³) work and “several seconds” at the largest preset on modest hardware; this is the authors’ warning, not an independent benchmark. The worker transfers the result, but falls back to synchronous computation if Workers are unavailable or construction fails, which can freeze the tab. Failed terrain tiles leave zero-filled elevation cells, so partial coverage can create false visibility; a drone implementation should track unknown cells explicitly. The root license is MIT ([LICENSE](https://github.com/opengeos/GeoLibre/blob/main/LICENSE)); no performance claim for moving observers is supported. |
| **3. QGroundControl** — [CameraCalc.cc](https://github.com/mavlink/qgroundcontrol/blob/master/src/MissionManager/CameraCalc.cc#L120-L157) | The inspected survey-camera calculations derive nominal image ground footprint from distance to surface, sensor/image dimensions, focal length, overlap and image density. This is mission-planning geometry, not a live gimbal camera ray and not terrain LOS. | Good reference for camera/survey terminology and parameters, but less directly useful than MissionPlanner for projecting a live pose. The project offers Apache-2.0/GPL-3.0 licensing at the repository level; confirm the exact applicable terms before reusing code. No comparable movement-performance evidence was found. |
| **4. DigitalArsenal/SensorShadow** — [SensorShadow.js](https://github.com/DigitalArsenal/SensorShadow/blob/main/src/SensorShadow.js), [README](https://github.com/DigitalArsenal/SensorShadow) | A real sensor-frustum shadow/visibility effect using a shadow map and shader classification, rather than a CPU DEM walk. | Cesium-specific and unsuitable as a MapLibre module. The repo declares Apache-2.0, but its small maintenance footprint (no releases observed) and private API coupling make it a pattern to study, not a foundation to adopt. |

## Practical boundary

Keep the continuously updated camera display as a projected footprint. If users later need “terrain between camera and point blocks the view,” make that an explicit, lower-frequency analysis over a bounded DEM. GeoLibre shows a comparatively small data path for that question, but its code still has meaningful correctness and latency tradeoffs. Neither its docs nor inspected source establishes acceptable performance when recomputed at drone telemetry rates.

These categories should stay visually distinct: a projected FOV footprint says where rays meet the assumed ground surface; a terrain viewshed says which sampled terrain cells are visible from an observer; a projected video overlay is a third capability.
